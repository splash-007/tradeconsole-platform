## 5. Mock Data Inconsistencies That Must Be Fixed

### 5.1 Customer Status Values
The application uses inconsistent customer status values across different files:

| File | Values Found |
|------|-------------|
| `agent.service.ts` | `pending`, `verified`, `active`, `suspended`, `rejected` |
| `marketing.service.ts` | `pending`, `verified`, `active`, `rejected`, `suspended` |
| `admin.service.ts` | `unverified`, `pending`, `verified`, `rejected` |

**Canonical backend value**: `pending | verified | active | suspended | rejected`  
`unverified` should be replaced with `pending`.

### 5.2 Task Status Values
| File | Values Found |
|------|-------------|
| `agent.service.ts` | `pending`, `in_progress`, `completed`, `overdue`, `cancelled` |
| `platform.service.ts` | `pending`, `in_progress`, `completed`, `unable_to_complete`, `cancelled`, `overdue` |

**Canonical backend value**: `pending | in_progress | completed | unable_to_complete | cancelled | overdue`

### 5.3 Staff/Presence Status
| File | Values Found |
|------|-------------|
| `agent.service.ts` | `online`, `busy`, `away`, `offline` |
| `staff-chat.service.ts` | `online`, `away`, `busy`, `offline` |
| `platform.service.ts` | `online`, `away`, `busy`, `offline` |

These are consistent — no fix needed.

### 5.4 Finance Status
| File | Values Found |
|------|-------------|
| `finance.service.ts` | `pending`, `processing`, `completed`, `failed`, `cancelled` |
| `admin.service.ts` | `pending`, `approved`, `rejected`, `processing` |

**Canonical deposit/withdrawal status**: `pending | processing | approved | rejected | completed | failed | cancelled`

### 5.5 Staff Role Key Naming
The `admin.service.ts` uses `super_admin` but `rbac.ts` defines both `super_admin` and `admin` as separate roles. This is correct and consistent.

### 5.6 Affiliate ID Format
Affiliates are referenced as `AFF-0042` (string code) in some places and as UUID-style IDs in others. The backend should use UUID primary keys with a separate human-readable `affiliate_code` column.

### 5.7 Customer Field Naming
| Mock Data | Recommended Backend |
|-----------|---------------------|
| `firstName` | `first_name` |
| `lastName` | `last_name` |
| `assignedAgent` | resolved via `customer_assignments` table |
| `accountBalance` | computed from `ledger_entries` |
| `totalDeposits` | computed from `deposit_requests` |
| `totalWithdrawals` | computed from `withdrawal_requests` |

## 6. Frontend Functionality That Cannot Be Supported Cleanly

### 6.1 Computed Balance Fields
The UI displays `accountBalance`, `availableBalance`, `reservedBalance`, `totalBalance` as direct fields. These **must not** be stored as editable columns. They must be computed from `ledger_entries` via the double-entry ledger. The API must return a balance DTO computed at query time.

### 6.2 "Tags" on Customers
The customer detail page shows `tags: ['VIP', 'High Value']`. This requires a separate `customer_tags` + `customer_tag_assignments` junction table, not a PostgreSQL array column.

### 6.3 Assignment History
The current mock data stores `history[]` inside the assignment object. This must be a separate `assignment_history` table with proper foreign keys.

### 6.4 Task Activity Log
Similarly, `activityLog[]` inside tasks must be a separate `task_activity_log` table.

### 6.5 KYC Steps
The UI shows step-by-step KYC progress. This requires either a `verification_steps` table or a JSONB `steps` column on `verification_cases`. We recommend JSONB for steps since the step structure is fixed and not queried individually.

## 7. Finalized Product Decisions

1. **Registration lifecycle**: A `registrations` record may exist without a `users` record. The full lifecycle is: `registration/lead → account request → Admin approval → async provisioning → users record created → activation email → customer sets password → activated`. Do not create `users`/`customer_profiles` immediately when a raw lead/registration is captured.

2. **First-login security**: Use a secure activation/set-password link. Do NOT email permanent or temporary plaintext passwords. `users.password_hash` may be NULL only before account activation. Once `account_activated = true`, a valid Argon2id hash is required. Activation tokens are stored hashed and expire.

3. **Login API**: Standardize central authentication around `{ "identifier": "username-or-email", "password": "string", "sourceSite": "optional-approved-marketing-domain" }`. One authentication system supports both direct Trade Console login and marketing-site login.

4. **Cross-domain login handoff**: No PostgreSQL `login_handoff_tokens` table. Tokens are stored hashed/derived in Valkey with ~60s TTL, single-use, deleted immediately on redemption. Audit records go to `audit_logs`.

5. **Marketing sites vs marketing sources**: `marketing_sites` is the approved authentication entry-point allowlist (separate table). `marketing_sources` is attribution/analytics data. Never accept arbitrary redirect/login URLs from the browser.

6. **KYC status**: Canonical statuses are `not_started | in_progress | submitted | under_review | additional_information_required | verified | rejected`. KYC is mandatory but presented under Profile/Settings rather than primary navigation. Document storage uses external S3-compatible object storage (Cloudflare R2 recommended). PostgreSQL stores object keys/metadata only.

7. **Double-entry ledger**: The production financial ledger is genuinely double-entry. Structure: `ledger_transactions → ledger_entries → accounts` — no mutable balance column. Every finalized ledger transaction must balance debits and credits. System/clearing/fee/settlement accounts are supported alongside customer accounts. Ledger entries are immutable and are the source of truth for all balances. A mutable customer balance field must NOT be used as financial source of truth.

8. **account_requests schema**: Canonical FK relationships — no ambiguous `customer_id` referencing either `users` or `registrations`. Use: `registration_id → registrations.id`, `provisioned_user_id → users.id` (nullable until provisioned), `requested_by_user_id → users.id`, `assigned_manager_id → users.id`, `marketing_site_id → marketing_sites.id`. No separate `account_request_audit` table — use existing `audit_logs`.

9. **Roles and permissions**: 23 canonical roles. Three-layer permission resolution: assignment-specific override → staff override → role default → deny. New permissions: `customer_account.*` (8 keys) and `marketing_site.*` (2 keys). Account-request authorization must additionally verify assignment/customer scope.

10. **Trading account separation**: `accounts` = fiat/cash account. `trading_accounts` = trading context. Separate tables.

11. **Document storage**: External S3-compatible object storage (Cloudflare R2 recommended). PostgreSQL stores object keys and metadata only. Binary document data is never stored in PostgreSQL.

12. **2FA**: TOTP only for Phase 1.

## 8. Architecture Principles Applied

- **UUID primary keys** for all externally-accessible records
- **TIMESTAMPTZ** for all timestamps (UTC)
- **NUMERIC(20,8)** for crypto quantities, **NUMERIC(18,2)** for fiat
- **Genuine double-entry ledger** — `ledger_transactions → ledger_entries → accounts` — no mutable balance column
- **Immutable audit log** — append-only, no UPDATE/DELETE — used for all account provisioning events
- **Normalized permissions** — role permissions + individual overrides + assignment-specific overrides
- **Assignment history** — never overwrite, always append
- **No domain hardcoding** — all external URLs from environment config
- **PII separation** — phone numbers stored only in `customer_profiles`, never in call records sent to browser
- **Presence in Valkey** — not PostgreSQL
- **Market data in Valkey/provider** — not PostgreSQL
- **Login handoff tokens in Valkey** — not PostgreSQL (ephemeral, ~60s TTL)
- **KYC document binaries in S3-compatible storage** — not PostgreSQL (keys/metadata only)
- **Sequential registration lifecycle** — `registrations` record may exist without `users` record

---

## 9. Domain Independence

The database contains **no hardcoded domain references**. All external URLs (API base, CDN, document storage, marketing site login URLs) are environment configuration or database-driven configuration. The schema is fully portable across domains.
