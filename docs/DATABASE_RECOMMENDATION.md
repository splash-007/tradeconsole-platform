## 5. Mock Data Inconsistencies That Must Be Fixed

### 5.1 Customer Status Values
The application uses inconsistent customer status values across different files:

| File | Values Found |
|------|-------------|
| `agent.service.ts` | `pending`, `verified`, `active`, `suspended`, `rejected` |
| `marketing.service.ts` | `pending`, `verified`, `active`, `rejected`, `suspended` |
| `admin.service.ts` | `unverified`, `pending`, `verified`, `rejected` |

**Canonical backend value**: `pending | verified | active | suspended | rejected`  
`unverified` should be replaced with `pending`.

### 5.2 Task Status Values
| File | Values Found |
|------|-------------|
| `agent.service.ts` | `pending`, `in_progress`, `completed`, `overdue`, `cancelled` |
| `platform.service.ts` | `pending`, `in_progress`, `completed`, `unable_to_complete`, `cancelled`, `overdue` |

**Canonical backend value**: `pending | in_progress | completed | unable_to_complete | cancelled | overdue`

### 5.3 Staff/Presence Status
| File | Values Found |
|------|-------------|
| `agent.service.ts` | `online`, `busy`, `away`, `offline` |
| `staff-chat.service.ts` | `online`, `away`, `busy`, `offline` |
| `platform.service.ts` | `online`, `away`, `busy`, `offline` |

These are consistent — no fix needed.

### 5.4 Finance Status
| File | Values Found |
|------|-------------|
| `finance.service.ts` | `pending`, `processing`, `completed`, `failed`, `cancelled` |
| `admin.service.ts` | `pending`, `approved`, `rejected`, `processing` |

**Canonical deposit/withdrawal status**: `pending | processing | approved | rejected | completed | failed | cancelled`

### 5.5 Staff Role Key Naming
The `admin.service.ts` uses `super_admin` but `rbac.ts` defines both `super_admin` and `admin` as separate roles. This is correct and consistent.

### 5.6 Affiliate ID Format
Affiliates are referenced as `AFF-0042` (string code) in some places and as UUID-style IDs in others. The backend should use UUID primary keys with a separate human-readable `affiliate_code` column.

### 5.7 Customer Field Naming
| Mock Data | Recommended Backend |
|-----------|---------------------|
| `firstName` | `first_name` |
| `lastName` | `last_name` |
| `assignedAgent` | resolved via `customer_assignments` table |
| `accountBalance` | computed from `ledger_entries` |
| `totalDeposits` | computed from `deposit_requests` |
| `totalWithdrawals` | computed from `withdrawal_requests` |

## 6. Frontend Functionality That Cannot Be Supported Cleanly

### 6.1 Computed Balance Fields
The UI displays `accountBalance`, `availableBalance`, `reservedBalance`, `totalBalance` as direct fields. These **must not** be stored as editable columns. They must be computed from `ledger_entries`. The API must return a balance DTO computed at query time.

### 6.2 "Tags" on Customers
The customer detail page shows `tags: ['VIP', 'High Value']`. This requires a separate `customer_tags` + `customer_tag_assignments` junction table, not a PostgreSQL array column.

### 6.3 Assignment History
The current mock data stores `history[]` inside the assignment object. This must be a separate `assignment_history` table with proper foreign keys.

### 6.4 Task Activity Log
Similarly, `activityLog[]` inside tasks must be a separate `task_activity_log` table.

### 6.5 KYC Steps
The UI shows step-by-step KYC progress. This requires either a `verification_steps` table or a JSONB `steps` column on `verification_cases`. We recommend JSONB for steps since the step structure is fixed and not queried individually.

## 7. Product Decisions Required Before Creating Migrations

1. **Multi-currency accounts**: Does each customer have one account (USD) or multiple currency accounts? The current UI shows a single USD balance. Recommend designing for multi-currency from the start.

2. **Trading account separation**: Is the trading account the same as the finance account, or separate? The UI shows both `portfolio` (trading) and `finance` (deposits/withdrawals) as distinct. Recommend separate `accounts` (finance) and `trading_accounts` tables.

3. **Affiliate commission model**: The UI shows revenue figures per affiliate but no commission rate or payout structure is defined. This must be decided before building the affiliate tables.

4. **Document storage provider**: KYC documents should not be stored as PostgreSQL binary objects. Decide on S3-compatible storage (MinIO, AWS S3, Cloudflare R2) before building the `verification_documents` table — the table will store file references, not binary data.

5. **Squaretalk integration**: The calling architecture is designed for Squaretalk but not yet integrated. The `calls` table design depends on what Squaretalk returns as session/call metadata.

6. **2FA method**: The application has a `two_factor_auth` table placeholder. Decide whether to support TOTP (Google Authenticator), SMS, or both.

7. **Soft delete vs. archive**: Decide which entities use `deleted_at` (soft delete) vs. a separate archive table. Recommendation: soft delete for customers, staff, assignments, tasks. Hard delete never for financial records.

8. **Ledger currency**: All current mock data uses USD. Confirm whether crypto balances (BTC, ETH) are tracked in the ledger or only in trading positions.

## 8. Architecture Principles Applied

- **UUID primary keys** for all externally-accessible records
- **TIMESTAMPTZ** for all timestamps (UTC)
- **NUMERIC(20,8)** for crypto quantities, **NUMERIC(18,2)** for fiat
- **Ledger-based finance** — no mutable balance column
- **Immutable audit log** — append-only, no UPDATE/DELETE
- **Normalized permissions** — role permissions + individual overrides + assignment-specific overrides
- **Assignment history** — never overwrite, always append
- **No domain hardcoding** — all external URLs from environment config
- **PII separation** — phone numbers stored only in `customer_profiles`, never in call records sent to browser
- **Presence in Valkey** — not PostgreSQL
- **Market data in Valkey/provider** — not PostgreSQL

---

## 9. Domain Independence

The database contains **no hardcoded domain references**. All external URLs (API base, CDN, document storage) are environment configuration. The schema is fully portable across domains.
